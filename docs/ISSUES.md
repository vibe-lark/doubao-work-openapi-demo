## ISSUE-001 · 无 token / 伪造 token 返回网关码 99991668 / 99991661，与文档错误码 401001 不一致

- **发现日期**：2026-10-09
- **最近复现**：2026-10-13（本工程 `test/run.js` B1/B2，PPE）
- **环境**：PPE（`https://open.feishu.cn/open-apis/agent`，带 `X-Tt-Env: ppe_doubao_oapi`、`X-Use-Ppe: 1`）；2026-10-09 当日也曾观测到另一码 99991661
- **接口**：全部业务接口（以 `GET /v1/sessions?page_size=1` 探测）
- **现象（真实脱敏证据）**：
  - 无 token：`HTTP 400`，`{"code":99991661,"msg":"Missing access token for authorization. Please make a ..."}`
  - 伪造 token（`Authorization: Bearer forged-token-for-boundary-test`）：`HTTP 400`，`{"code":99991668,"msg":"Invalid access token for authorization. Please make a ..."}`
  - 2026-10-09 的首次联调中，无 token 曾返回 `99991668`（另有一次 `99991661`），即两个码在不同时间都出现过。
- **文档预期**：通用约定错误码表写明未授权为 `HTTP 401 / code 401001`（前三位与 HTTP 状态码一致）。
- **根因分析（推测）**：请求可能先被飞书开放平台网关鉴权层拦截，返回的是账号体系网关码（9999166x），尚未进入豆包业务网关的错误码映射层；HTTP 类别也从 401 变成了 400。
- **状态**：**待平台确认**
- **解决日期**：—
- **解决方案 / 规避建议**：
  1. 请确认豆包网关是否已规划把 99991661/99991668 统一映射为文档承诺的 `401 / 401001`；
  2. 若短期不映射，建议在错误码文档补充「网关层鉴权错误码」一节，列出 99991661/99991668 的触发条件与处理建议；
  3. 客户端侧临时把 `99991661/99991668` 与 `401001` 同等视为「需要重新授权」，但不应把它写死成业务契约。

## ISSUE-002 · 开启 IP 白名单后非白名单出口统一返回 99991401，与鉴权错误难以区分

- **发现日期**：2026-10-12
- **环境**：线上与 PPE 均复现
- **接口**：全部业务接口
- **现象（真实脱敏证据）**：应用开启 IP 白名单后，非白名单出口 IP 的请求返回 `HTTP 400`，body 中 `code=99991401`，`msg` 形如 `ip x.x.x.x is denied by app setting`。
- **文档预期**：文档未说明 IP 白名单拦截的返回形态；该码与 token 类错误（9999166x）同样落在 400 段，客户很难从返回判断「该去加白 IP」而不是「该换 token」。
- **根因分析**：IP 白名单在网关准入层拦截，错误沿用账号体系网关码，未进入豆包业务错误码体系。
- **状态**：**已规避**（客户侧把出口 IP 加白即可恢复）；**文档说明待研发补充**
- **解决日期**：2026-10-12（客户侧加白后恢复）
- **解决方案 / 规避建议**：
  1. 客户侧：在应用安全设置里把服务器出口 IP 加入白名单（本地演示默认出口为办公网/机房 NAT IP）；
  2. 建议研发在文档区分三类「400 段网关错误」：token 缺失/失效（9999166x）、IP 未加白（99991401）、参数非法（400001），并给出各自排查动作。

## ISSUE-003 · 旧版 OAuth 流程的 user_access_token 被豆包 API 拒绝，文档未显式声明不兼容

- **发现日期**：2026-10-12（客户真机确认）
- **环境**：线上
- **接口**：令牌端点 + 全部业务接口
- **现象（真实脱敏证据）**：
  - 使用旧版流程（`authen/v1/access_token` 换 token，授权时不显式申请 scope）得到的 `user_access_token` 调豆包接口被拒；
  - 改用新版 v3：授权端点 `accounts.feishu.cn/open-apis/authen/v1/authorize` 且**显式带 `doubao:*` scope**、换 token 走 `accounts.feishu.cn/oauth/v3/token` 后正常。
- **文档预期**：旧版获取 user_access_token 的接口官方已标注「历史版本，不再维护」；但豆包工作 OpenAPI 文档没有显式声明「旧流程 token 不适用于本 API、必须使用显式 doubao scope 的 v3 流程」。
- **根因分析**：豆包接口以新版 scope（`doubao:session:read` 等）做鉴权，旧流程 token 不携带这些 scope 授权。
- **状态**：**已规避**（统一走 v3 + 显式 scope）；**待文档明确**
- **解决日期**：2026-10-12
- **解决方案 / 规避建议**：
  1. 授权 URL 必须带 scope：`doubao:session.event:write doubao:session.message:read doubao:session:write doubao:session:read doubao:session.event:read doubao:file:write`；
  2. 换 token 与刷新都用 `/oauth/v3/token`；
  3. 建议在豆包接入文档显著位置写明「仅支持显式申请 doubao scope 的新版 v3 用户 token，旧版无 scope token 不兼容」。

## ISSUE-004 · user_access_token 有效期很短（约 1 小时量级），刷新失败后「连接还在但业务 NOT_CONNECTED」

- **发现日期**：2026-10-09
- **环境**：PPE / 线上
- **接口**：OAuth 刷新 + 业务接口
- **现象（真实脱敏证据）**：真机使用中 token 约 1 小时即失效；当 refresh 链路失败（refresh_token 轮转/过期或网络问题）时，前端连接状态仍显示已连接，但业务调用实际失败，表现为代理层拿不到可用 token，返回 `NOT_CONNECTED` 式错误。
- **文档预期**：文档未在豆包 OpenAPI 章节给出 user_access_token 的具体有效期与 refresh_token 的轮转规则（是否一次性、有效期、宽限期）。
- **根因分析**：token TTL 短 + 刷新失败后的状态语义不清，UI 容易误报「已连接」。
- **状态**：**待确认**（有效期与刷新轮转行为需在真机跨过期时刻实测补全；本工程 O5 用例覆盖该测量，具备 client_id/secret 时可直接跑）
- **解决日期**：—
- **解决方案 / 规避建议**：
  1. 工程侧：到期前 2 分钟自动刷新；刷新失败立即把连接态降级并引导重新授权（本工程 `server/lib/upstream.js` 已实现）；
  2. 建议研发明确文档：access_token TTL、refresh_token 是否轮转及 TTL、刷新失败时建议的重试/退避策略。

## ISSUE-006 · 固定回调 127.0.0.1 在云端/无本机服务场景打不开，文档缺手动 code 流程

- **发现日期**：2026-10-09
- **环境**：云端部署 / 反向代理托管场景
- **接口**：OAuth 回调
- **现象**：登记的重定向 URI 固定为 `http://127.0.0.1:4110/api/auth/feishu/callback`。在云端浏览器打开授权页后，浏览器会尝试跳到用户本机 127.0.0.1:4110；若本机没起服务，页面打不开，code 拿不到。
- **文档预期**：文档主要描述标准回调接收，对「本机无服务」的备用流程缺少说明。
- **根因分析**：演示应用没有公网回调地址，只能登记本机地址；授权 code 出现在跳转地址里，可手动提取。
- **状态**：**已规避**
- **解决日期**：2026-10-09（本工程实现备用流程）
- **解决方案 / 规避建议**：本工程同时提供两条路径：
  1. 本机 `node server/server.js` 起在 4110，浏览器自动接住回调并换 token；
  2. 云端/无本机服务时，授权后从浏览器地址栏复制裸 `code` 或整段回调 URL，在首页粘贴（`POST /api/auth/manual-code`），服务端提取 code 并完成换取。
  建议文档补充该手动流程，降低云端演示门槛。

## ISSUE-008 · 409001 与 interrupt 用例依赖真实 in_progress 时间窗，自动化无法稳定复现

- **发现日期**：2026-10-09
- **环境**：PPE
- **接口**：Events Create（连发 user.message / user.interrupt）
- **现象**：`409001 session has a message in progress` 与 `user.interrupt → cancelled` 都要求第二步精确落在回复生成窗口内。真机回复耗时不稳定（短则一两秒），自动化轮询常常抢不到窗口，导致用例偶发失败，且这类失败不应误判为平台缺陷。
- **文档预期**：in_progress 连发第二条应返回 409/409001；in_progress 打断应受理并最终 cancelled，半截文本保留。
- **根因分析**：时序敏感，非确定性问题。
- **状态**：**待确认**（文档行为本身明确，待稳定复现手段/更合适的长任务 prompt）
- **解决日期**：—
- **解决方案 / 规避建议**：
  1. 本工程 S7/B22 采用「发起长任务 + 快速轮询状态 + 进入 in_progress 立即执行第二步」，并做 2–3 次重试；抢不到窗口一律如实标 BLOCKED，绝不伪造 PASS；
  2. O4 验证打断后 session 恢复 idle 且可继续对话；
  3. 建议研发提供稳定进入 in_progress 的调试手段（如固定长回复的测试 prompt、测试专用延迟开关），便于验收 409001 与 cancelled 语义。
